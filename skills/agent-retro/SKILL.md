# Agent retro

Find changes to the agent's environment that would have prevented the trouble in these sessions. Change nothing until the user accepts a fix.

## Steps

1. Run `uv run --no-project scripts/collect.py --since <date>` from this skill's directory. Without a timeframe, review the current session instead.
2. Search the logs for trouble before reading them in full: user corrections, interrupts, denied or failed tool calls, approval and sign-in prompts, browser automation, content the user pasted in, reverted edits, repeated searches, repeated review findings, outlier `tokens` or `turns` in `sessions`, and commands or inline scripts repeated across sessions. Read the excerpts around each. Then read every PR comment and review the script lists.
3. Group the trouble by cause. Across several sessions, keep a cause only when it appears in at least two sessions or pull requests, in any mix. Count a subagent or review thread as part of the session that started it. Tag each cause as global, specific to one repo, or specific to one tech stack.
4. For each `Remove-When:` trailer the script lists, check its condition and whether the cause its commit names recurred. Propose deleting a fix whose condition holds, that a higher-tier fix now covers, or that misfires. Propose a higher-tier fix for a cause that recurred after its fix. Also audit every entry under `routines` and, when T3 Code's `list_scheduled_tasks` is available, every scheduled task across projects: flag any job that runs more often than hourly without needing to, pins a recurring sweep to a long thread, lacks a quiet-when-nothing rule, or is dead, finished, or duplicated.
5. When the script ran, read each memory it lists, and check every claim it makes about files, commands, tools, or dates against the current files and the logs. Give it one outcome: promote its lesson to a `memory` cause, tagged as in step 3, and propose deleting the memory once that cause's fix lands; propose corrected text, citing the file or log that contradicts it, when a claim is wrong but the memory still records state no fix can hold; propose deleting it when its point no longer holds or an existing fix covers it; or keep it when it records state no fix can hold, such as a project's next steps, in a folder later sessions open. `sessions` counts the logs still on disk for the folders that load a memory; no later session opens a per-thread scratch folder. Never propose deleting a Codex memory: Codex regenerates its memory files from its sessions.
6. Propose a fix for each cause from the categories below, in the place its tag points to. Prefer, in order: config or an installed tool; a script, lint rule, compiler deprecation, or CI check; a harness hook; a skill; an always-loaded instruction. A new lint rule or CI check also migrates the code it would flag on the default branch, to any shared helper that already does the job, because agents copy the patterns they find. Name a past mistake from the evidence that the new check would fail on, and give the error it prints, naming the code to write instead. When a cause breaks a rule an instruction file lists as unchecked, propose a check and moving the rule to the checked list. For a hook or anything after it, name the higher-tier fix you ruled out. A hook runs on every matching call in one harness, so match narrowly, print only on a hit, and name what other harnesses lose. Give each workaround, a fix that makes up for a missing tool, model, or upstream capability, a `Remove-When:` trailer for the commit that adds it, naming that capability's arrival in a form you can check with the fix still in place; a cause stays absent while its fix works, so its absence can't show the fix is unneeded. A fix that records a preference or policy no model could infer, such as where the user keeps checkouts, gets no trailer; say so in its commit body. A workaround that is a hook denying calls is the exception, since the denied attempts still reach the logs: start its message with a fixed tag, such as `[t3-worktree-hook]`, and give it the condition that no log from the last 30 days contains the tag. Search 30 days of logs for that tag, even when the timeframe is shorter. Apply `write-for-agents` to any instruction you propose.
7. Rank the candidates by how often each recurred and what it cost. Give each its category, tag, evidence (session or pull request, date, and a short quote, or a memory path, with secrets redacted), and proposed fix. Mark a cause whose fix already exists as fixed, and say how to confirm the fix took effect. Name the harnesses the script read, and quote any error it printed. Finish when every cause from steps 3 and 5 has a candidate and every trailer and routine finding from step 4 and memory from step 5 has an outcome.
8. When you run as a subagent, or the user asked for a report, return the ranked candidates. Otherwise walk the user through them one at a time, in rank order, each with its evidence and your recommendation, and wait for an answer before the next. Make each fix the user accepts in the repo it belongs to, and open a pull request that cites its evidence unless that repo's instructions say to commit directly. Finish when every candidate is accepted, rejected, or deferred.

## Categories

- `navigation`. The agent took long to find a file or fact, or missed a hidden dependency between files. Add a pointer where the agent looked first.
- `checks`. The agent made a mistake an automated check could catch, or the repo runs no lint, type, or test check before merge. Read the repo's check commands and CI first; a check that exists but is unwired or broken is the finding.
- `codify`. Agents repeated mechanical work across sessions, such as polling a status, writing an API client, extracting logs, or running setup steps. Propose a checked-in script or task-runner target that exits nonzero on failure, in the repo the work belongs to.
- `review`. A review agent or skill missed a mistake, or keeps flagging the same one. Give a mechanical violation, such as a banned API or import shape, a deterministic check: a lint rule, hook, or CI job. Keep review rules for judgment calls.
- `instructions`. The agent ignored or misread an instruction file or skill, a skill fired when it shouldn't or stayed silent when it should have fired, or an instruction changes nothing. Fix the wording before moving the instruction.
- `memory`. A memory holds a lesson that reaches only one harness or the sessions started in one folder. Put the fix where every session that needs the lesson reads it.
- `tools`. The agent made expensive or repeated tool calls, a session burned outlier tokens, a scheduled routine wastes tokens or noise or is dead or duplicated, or a tool or MCP server wastes tokens. For an MCP server that fails or asks for sign-in where a CLI for the same service works, propose removing the server.
- `access`. The agent lacked information it needed, such as server logs or read-only access to a service, or reached a service through browser automation or content the user pasted in where an MCP server or CLI could have done the same job. Propose the service's MCP server, or its CLI when one is already installed and working, and name the sign-in it needs.
